## Rules for this port

- The upstream `AGENTS.md` approval to erase `userdata` was given by the sweet
  owner for sweet. **It does not apply here.** Every destructive step on surya
  (flashing `userdata`, anything beyond `fastboot boot`) needs explicit
  approval from the surya owner first, with the risk explained.
- Never boot or flash a sweet image on surya.
- Back up `persist`, `modemst1`, `modemst2`, `fsg`, `fsc`, `boot`, `dtbo`,
  `vbmeta` before any install step. Keep dumps out of git (`backup/`, `dtb/`
  are already ignored).
- Go one step at a time; record observed results here and keep them separate
  from guesses.

## Touch plan (research 2026-10-23)

Hardware (live DT): `spi@0x880000` `qcom,spi-geni` = QUP wrapper 0 SE0 (wrapper
`qupv3_0_geni_se@0x8c0000`), clocks `se-clk`/`m-ahb`/`s-ahb` (GCC phandle 0x27, ids
0x44/0x67/0x68), IRQ SPI 0x259, GPI DMA available but not required; pins
`qupv3_se0_spi_active`: gpio49–52, function `qup00`; device `novatek,NVT-ts-spi` CS0,
8 MHz, reset GPIO 8, irq GPIO 9 (falling), `novatek,swrst-n8-addr = 0x3f0fe`,
`novatek,spi-rd-fast-addr = 0x3f310`; supplies vddio + LAB/IBB (panel rails, already on).

Reference driver: `sm7150-mainline/linux` (HEAD `fd78d179`)
`drivers/input/touchscreen/nt36xxx_{core,spi}.c`, `nt36xxx.h`:
- SPI framing (`nt36xxx_spi.c`): page select `ff XX YY` (addr bits 23..16, 15..7) as one
  write, then read = `addr&0x7f` byte followed by data; write = `(addr&0x7f)|0x80` + data.
  SPI mode 0, 8-bit, ≤ 8 MHz.
- Chip ID (`trim_id_table`): NT36675-class map for ids `xx xx xx 75 66 03` and
  `0C xx xx 72 66 03`; memory map `nt36675_memory_maps` (event buffer `0x22D00`,
  boot-ready `0x3F10D`, `SWRST_N8 0x3F0FE`, `SPI_RD_FAST 0x3F310`, eng reset `0x7FFF80`).
- **Firmware is host-loaded at every power-on**: `request_firmware(firmware-name)` →
  `_nt36xxx_boot_download_firmware` (ILM/DLM partitions parsed by `nvt_bin_header_parser`,
  HW CRC check). Blob: `novatek_ts_huaxing_fw.bin` (see above).
- Reports: `nt36xxx_report` reads `POINT_DATA_LEN` (65) bytes from the event buffer,
  10 fingers.

XNU side (sweet patch 0060 `bsd/dev/sweet_touch.c`): one polling kernel thread, GENI
register access through `ml_io_map`, GCC clock vote + TLMM GPIO setup, delivers
`sweet_hid_touch(finger, down, x, y)` to the existing SweetHIDTouch digitizer service
(0062/0063 add RPMh rail + Goodix packing). A surya driver can reuse the thread, GENI
helpers and `sweet_hid_touch`, replacing the bus (I²C → SPI on SE0) and protocol
(Goodix → Novatek incl. firmware download).

Steps:
- 3a read-only shim probe: GCC SE0/wrapper clock status, SE0 `GENI_FW_REVISION`
  (protocol: 1 = SPI expected), TLMM gpio8/9/49–52 config — no writes.
  Implemented: `shim/surya_touch.c` (`-DSURYA_TOUCH_PROBE`, only in build-surya.sh),
  runs on the no-payload path before the UFS probe. GCC: vote `0x5200c` bits 6–10,
  CBCRs `0x17004/08/0c/14/30` (from `drivers/clk/qcom/gcc-sm7150.c`); skips SE reads if
  the QUP0 AHB clocks report CLK_OFF.
  **Result 2026-10-23 17:24** (`evidence/2026-10-23-touch-3a-spi-probe.jpg`):
  GCC vote `0x5200c=0x41000000` (APPS votes none of QUP0 bits 6–10); CBCRs m_ahb=0,
  s_ahb=0, core=0x4220, core2x=0x4220 (all running, voted by someone else), **SE0 CBCR
  0x80004220 = CLK_OFF** (SE clock gated); QUP0 hw_ver 0x20000000 (v2.0 → SPI
  oversampling 1); **SE0 FW revision 0x101 → protocol 1 = SPI, firmware loaded**;

### G2: CX power-on (patch 0100, boot-arg sweetgpu=2)
First write step. Register numbers/sequences from the open-source Qualcomm drivers for this clock
controller (Linux gpucc-sc7180.c - also serves the Adreno 618 - gcc-sm7150.c, gdsc.c, clk-rcg2.c),
checked against surya-dump/live.dts. CX side only; GX is left off (gpucc-sc7180 gives gx_gdsc
gdsc_gx_do_nothing_enable: the GMU owns GX, software must not collapse/enable it - that is a later step).
Steps, each read back and logged "SWEET GPU: ...", aborts if CX GDSC does not reach PWR_ON:
 1. Vote GPLL0 + GPLL0_DIV for the GPU: GCC 0x52004 |= BIT(15)|BIT(16).
 2. GPU-side GCC branches on (BIT(0)): cfg_ahb 0x71004, memnoc_gfx 0x7100c, snoc_dvm_gfx 0x71018.
 3. CX GDSC on (votable): clear SW_COLLAPSE (0x106c BIT(0)), poll PWR_ON (BIT(31)).
 4. GMU clock source to 200 MHz: CFG 0x1124 = 0x602 (src 6 = GPLL0_OUT_MAIN_DIV, hid_div 2 = /1.5),
    then CMD_UPDATE (0x1120 BIT(0)), poll until it clears.
 5. CX branches on (set BIT(0), poll BIT(31) clear): cxo_aon 0x1004, cxo 0x109c, cx_gmu 0x1098,
    cx_snoc_dvm 0x108c, crc_ahb 0x107c.
Nothing flashed; a reboot restores the boot loader's state. Test: boot sweetgpu=2, then
`grep -a "SWEET GPU" logs/testNN.txt`. Expect cx_gdscr -> PWR_ON, gmu rcg updated, branches "on".
Next (G3+): GPU SMMU context, then GMU firmware load + HFI (needs a618_gmu.bin), per the a6xx_gmu.c order.

### Bluetooth: WCN3990 over GENI HS-UART - groundwork (2026-11-03)

and we ALREADY have a working GENI serial-engine driver (the GENI I2C in patches 0060/0063). A GENI UART
is the same SE block with a different protocol config + the S (secondary) channel for RX. Two real
blockers remain, both shared with other subsystems: powering the chip's rails (regulator/PMIC - see the
cross-cutting note below) and bridging QCA HCI to iOS's own BT transport (the Apple-specific hard part).

### Cross-cutting blocker: regulator / PMIC control (camera C2b, Bluetooth B3, audio)
Several subsystems stall at the same place - turning on a power rail. GOOD NEWS: we already have a general
SPMI read/write to any APPS-owned PMIC peripheral (sweet_spmi.c, patch 0083: sweet_spmi_init/read/write),
and the camera/BT rails are plain PMIC LDOs on the SPMI bus - so we may be able to force a rail on directly
over SPMI (write ENABLE +0x46 bit0x80, like SweetBacklight enables WLED) instead of building a full RPMh
stack. The catch: these LDOs are modeled as RPMh-managed (qcom,rpmh-vrm-regulator), so a direct SPMI write
only sticks if the LDO's SPMI peripheral is APPS-owned (not AOP/RPMh-owned); sweet_spmi_write already checks
that and refuses otherwise. R1 (below) answers it.

Verified rail -> LDO -> SID map (surya-dump/live.dts; SIDs pm6150=0, pm6150l=4, pm8009=0xa, all on
qcom,spmi@c440000). pmic5 LDO SPMI peripheral base = 0x4000 + 0x100*(n-1). Common LDO regs (Linux
qcom_spmi-regulator.c): TYPE +0x04 (0x04=LDO, 0x21=ULT_LDO), VOLTAGE_RANGE +0x40, VOLTAGE_SET +0x41,
ENABLE +0x46 (bit0x80 = on):
  cam_vio     = pm6150_l13  (sid 0, base 0x4c00)        cam_vana = pm8009_l6  (sid 0xa, base 0x4500)
  bt_vdd_io   = pm6150_l10  (sid 0, base 0x4900)        bt_vdd_core = pm6150l_l2  (sid 4, base 0x4100)
  bt_vdd_pa   = pm6150l_l10 (sid 4, base 0x4900)        bt_vdd_xtal = pm6150l_l1  (sid 4, base 0x4000)
  (cam_vdig = phandles 0x507/0x508, LDO name not resolved in DT - identify before C2b.)

STAGED PLAN:
  - R1 (WRITTEN, patch 0103, boot-arg sweetreg=1): read-only. For each rail's LDO, sweet_spmi_read TYPE,
    ENABLE, VRANGE, VSET and print. Self-validating (TYPE=0x04/0x21 confirms SID+base). Tells us which
    rails the boot loader already left on, and that the peripherals are reachable. Zero risk. Not yet built.
  - R2 (next, after R1 result): sweet_spmi_write ENABLE|0x80 (and VSET if needed) to turn one rail on; the
    write self-reports if the APID is not APPS-owned (then we need the RPMh path instead). Add the target
    LDO addrs to sp_write_allowed() in sweet_spmi.c first.
  - If direct SPMI is refused (AOP-owned): build a minimal RPMh path - apps_rsc (DT label apps_rsc, line
    ~3969/6821) TCS registers + cmd-db@c3f000c resource lookup (resource names e.g. "ldoa13") to send a
    VRM enable command. Bigger; only if R2 shows we must.
Once a rail can be turned on, camera C2b (sensor chip-id) and BT B3 (power WCN3990) both unlock.

### G4 plan: GMU firmware load + boot (recipe from mainline a6xx_gmu.c, 2026-11-05)
G4 wakes the GMU microcontroller - the real "turn the GPU on". It does NOT need the PMIC rails (runs on the
CX GDSC we already power in G2). Boot recipe (mainline a6xx_gmu_fw_start/_start, cold boot, legacy a630/a615):
  1. GENERAL_7 = 1 (register retention).
  2. RPMh init (a6xx_gmu_rpmh_init): program the RSCC (GMU+0x23000) + PDC cfg(0xb290000)/seq(0xb490000) sleep/
     wake sequences. *** SoC-SPECIFIC and the hard part - SM7150 values differ from SDM845/SM7325; must come
     from HakiOS hakios-sm7325 (closest a6xx XNU port), the surya vendor kgsl, or the GMU fw's embedded data.
  3. Load firmware: reject if > 0x8000 bytes; copy a630_gmu.bin as u32 words into CM3_ITCM_START + i (flat,
     no header parse - the simple legacy path).
  4. CM3_FW_INIT_RESULT = 0; CM3_BOOT_CONFIG = 0x02.
  5. HFI_QTBL_ADDR = hfi queue iova (needs GMU SMMU + a mapped HFI buffer - depends on a GMU context bank);

  8. start: CM3_SYSRESET=1 then =0; POLL CM3_FW_INIT_RESULT == 0xbabeface (interval 100, timeout 10000).
     *** THIS is the G4 milestone: 0xbabeface = the GMU firmware booted. ***

### Camera (surya): the hardest subsystem - groundwork only (2026-11-03)
HONEST CEILING FIRST. A working camera is further off than the GPU, for two stacked reasons:
  1. The sensors are the easy part. The real work is Qualcomm's **Spectra / Titan ISP** (CSIPHY -> CSID ->
     IFE/VFE -> IPE/BPS -> ICP), a large opaque pipeline that needs its own firmware (ICP a5xx fw) and a
     CDM command-buffer driver. That is the whole camss subsystem, comparable in size to the audio ADSP.
  2. iOS has NO driver that can talk to any of it. `AppleCamera`/`AppleH*ISP` target Apple's own ISP over
     Apple IOKit. To surface frames to AVFoundation we'd have to write a capture provider from scratch
     (a CoreMediaIO/IOKit source feeding AVCaptureSession) on top of a from-scratch Spectra driver.
So a live preview is a multi-month effort, not a near-term milestone. What IS tractable and PC-free to
prepare now is the hardware map + the one verifiable first step: talk to a sensor over CCI and read its
chip-ID (analogous to GPU G1/G2 - "it's alive" before anything renders).

VERIFIED HARDWARE MAP (from surya-dump/live.dts):
  - camcc (camera clock controller): base 0xad00000 size 0x10000, compat "qcom,camcc-sdmmagpie",
    vdd_cx + vdd_mx. phandle 0x29. (Same family as gpucc; register style matches the GPU clock work.)
  - titan_top_gdsc: /soc/qcom,gdsc@ad0c1c4 (power domain for the whole ISP/Titan block).
  - CCI0 (I2C): 0xac4a000 size 0x1000, IRQ GIC-SPI 460 (0x1cc), 2 masters (DATA0/CLK0, DATA1/CLK1),
    clock cci_0_clk_src 0x23c3460 Hz (~37.5 MHz). CCI1: 0xac4b000, IRQ SPI 461 (0x1cd), master2.
    CCI is just a dedicated Qualcomm I2C master block - this is the part we can drive without the ISP.
  - CSIPHY x4: 0xace0000, 0xace2000, 0xace4000, 0xace6000 (MIPI D-PHY; needed for frames, not for CCI).
  - CPAS-CDM0: 0xac48000 (cam170-cpas-cdm0, the command-DMA front end; client "ife").
  - ICP firmware node msm_cam_icp_fw + cpas client list: csiphy0-3, cci0-1, csid0-2, ife rdi/nrdi 0-2,
    ipe0-1, bps0, icp0, jpeg-dma/enc, fd0, lrme - i.e. the full Spectra pipeline is present in DT.
  - 7 cam-sensor nodes (cci@ac4a000 has @0..@6; cci@ac4b000 is the 2nd controller). Per node DT gives:
    csiphy-sd-index, cci-master, cci-device, MCLK (camcc clk id), reset/standby GPIOs on TLMM (phandle
    0x17b), and regulators (cam_vio ~1.8V, cam_vana ~2.8V, cam_vdig ~1.05-1.2V, cam_vaf for the actuator).
    NOTE: the DT does NOT carry each sensor's I2C slave address or sensor-id register - those live in the
    vendor camera config (camxoverridesettings / sensor module libs), not in the kernel DT. Must be pulled
    from a surya vendor image or a sensor datasheet before C2.
  - Sensors by role (public POCO X3 NFC spec; only the main is named in the open device tree):
    main/wide 64MP = Sony IMX682 (chip-id reg 0x0016, id 0x0682, 16-bit addr - standard Sony); ultrawide
    13MP, macro 2MP, depth 2MP, front 20MP = models not in the open tree (TBD from vendor config).

CCI PROGRAMMING MODEL (verified from mainline drivers/i2c/busses/i2c-qcom-cci.c):
  regs: CCI_HW_VERSION 0x00; CCI_RESET_CMD 0x04 (mask 0x0f73f3f7); CCI_QUEUE_START 0x08; CCI_HALT_REQ 0x34
    (M0 BIT0, M1 BIT1); IRQ block at 0xc00: GLOBAL_CLEAR_CMD 0xc00, MASK_0 0xc04, CLEAR_0 0xc08, STATUS_0 0xc0c.
  per-master (m): SCL_CTL 0x100+0x100*m, SDA_CTL_0/1/2 0x104/0x108/0x10c+0x100*m, MISC_CTL 0x110+0x100*m,
    READ_DATA 0x118+0x100*m, READ_BUF_LEVEL 0x11c+0x100*m.
  per-master/queue (m,n): EXEC_WORD_CNT 0x300+0x200*m+0x100*n, CUR_WORD_CNT 0x304+.., CUR_CMD 0x308+..,
    REPORT_STATUS 0x30c+.., LOAD_DATA 0x310+0x200*m+0x100*n.
  IRQ bits: M0 RD_DONE bit0, M0 Q0/Q1 REPORT bit4/bit8; M1 RD_DONE bit12, REPORT bit16/bit20; RST_DONE bit24.
  queue opcodes: SET_PARAM 1, REPORT 8, WRITE 9, READ 10.
  read N bytes from sensor reg (combined write-addr then read):
    Q0: LOAD_DATA SET_PARAM|(slave<<4); LOAD_DATA WRITE|(len<<4) + reg-addr bytes (4/word, LE);
        LOAD_DATA REPORT|REPORT_IRQ_EN; set EXEC_WORD_CNT=CUR_WORD_CNT; QUEUE_START BIT(m*2+0).
    Q1: LOAD_DATA SET_PARAM|(slave<<4); LOAD_DATA READ|(N<<4); EXEC_WORD_CNT=CUR_WORD_CNT; QUEUE_START BIT(m*2+1);
        poll READ_BUF_LEVEL (expect N/4+1 words); read READ_DATA, discard the first byte, take N bytes.
  (Downstream "qcom,cci" is the same HW; use these mainline-verified offsets. Needs camcc gate + titan GDSC
   + the CCI branch clock on before any of this; the clock IDs are in camcc, same approach as the GPU clocks.)

STAGED PLAN (mirrors GPU G-series; one verifiable step at a time):
  - C1 (read-only, no power change): map camcc 0xad00000, titan gdsc 0xad0c1c4, CCI0 0xac4a000, CCI1
    0xac4b000; dump HW_VERSION + GDSC/clock state. Pure observation, zero risk - same shape as GPU G1.
    WRITTEN: patch 0101 (SweetCamera.cpp, boot-arg sweetcam=1, printf "SWEET CAM: ..."). Reads PLL0,
    titan_top_gdsc (0xc1c4), cci_0/1 CBCR (0xb0f0/0xb164), cci_0 + mclk0..4 RCGs (0xb0d8, 0x4004..0x4084);
    reads CCI0/CCI1 HW_VERSION only if cci_0_clk is on AND titan GDSC PWR_ON (bus-stall guard, like G1's AHB
    check). camcc offsets from camcc-sc7180 (sibling of sdmmagpie); titan gdscr 0xc1c4 = DT abs 0xad0c1c4 -
    base. Verified CCI offsets from mainline i2c-qcom-cci.c. Dry-run applies clean; not yet built/tested.
  - C2 ("it's alive", split in two): the full sensor-id read needs the sensor rails (cam_vio/cam_vdig =
    PMIC LDOs - blocked, see cross-cutting note) + MCLK + reset-GPIO deassert, so it is split:
    * C2a (WRITTEN, patch 0102, boot-arg sweetcam=2): power the CCI *controller* only - bring the titan
      GDSC up (clear SW_COLLAPSE, poll PWR_ON, exactly like the GPU CX GDSC in G2), enable the cci_0_clk
      branch, reset CCI, read HW_VERSION with the block powered. On-die only, no PMIC. Bounded/verifiable:
      a sane HW_VERSION = we can power and reach CCI. Guards: aborts safely if titan won't power or the
      CCI RCG root is off (C1 shows the RCG state). Dry-run applies on top of 0101; not yet built/tested.
    * C2b (blocked on regulators): once a rail can be turned on, add MCLK0 enable + reset-GPIO deassert +
      the CCI I2C read. VERIFIED read recipe for sensor@0 (IMX682, cci-master 0):
        slave 0x1A (7-bit; Sony main-sensor addr, confirm vs vendor config), reg 0x0016 (16-bit addr),
        read 2 bytes, expect 0x0682 (same family as IMX412/IMX577 whose driver reads 0x0016).
        CCI queue (mainline i2c-qcom-cci.c): set i2c timing (DT i2c_fast_mode) first; Q0 SET_PARAM|(0x1A<<4),
        WRITE|(2<<4)+{0x00,0x16}, REPORT; run (QUEUE_START BIT(0)); Q1 SET_PARAM|(0x1A<<4), READ|(2<<4);
        run (QUEUE_START BIT(1)); READ_BUF_LEVEL then READ_DATA, discard first byte, take 2.
  - C3+ (frames): CSIPHY lane bring-up -> CSID -> IFE RDI path to DMA raw Bayer into memory. Large.
  - C4+ (processed): ICP firmware load + IPE/BPS via CPAS-CDM for YUV. Very large + needs ICP fw blob.
  - C5+ (iOS): a CoreMediaIO/IOKit capture provider so AVFoundation/Camera.app sees it. From scratch.
